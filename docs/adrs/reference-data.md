# ADR — `referenceData` / `informationDomains`: flat, domain-organized structured data

## Context

Some of what a project needs to document is not prose but small structured facts meant to be read with certainty by an external integration — a status enum with associated colors, a CDE folder structure, the set of required metadata fields per file. Earlier design work explored putting this inside a standard's own markdown frontmatter (a `data:` YAML block, referenced from the document body via a `document.data.*` directive). That approach was built, then discarded before being committed: scoping the data to one document meant two standards needing the same structured facts (e.g. the same status enum) would have to duplicate it, with no mechanism to keep the copies in sync — the exact problem live references already solve for teams/members/etc., just not yet solved for this kind of shared-but-not-quite-an-entity data.

## Decision

**`informationDomains` and `referenceData` are two new top-level BEP arrays.**

```typescript
InformationDomain = { id: string, name: string, description?: string }

ReferenceNode = {
  id: string               // UUID, auto-generated — opaque, never authored by hand
  informationDomainId: string // ref InformationDomain.id
  key: string               // unique among siblings sharing the same informationDomainId + parentId — not global; used to build the resolved object
  label: string              // human-readable identification for this node — required
  description?: string
  parentId?: string         // ref ReferenceNode.id — omitted for a root node
  data?: Record<string, JsonValue>  // free-form; a string value may embed a {{JSONata expression}} reference
}
```

An information domain (`topics`, `cde`) is a discoverable, describable category — `description` exists specifically so an external integrator can read what a domain represents before consuming its data. `InformationDomain` names the concept generally (a topic the project has information about), not narrowly as "structured data grouping": a standard can also associate itself with the same domain to indicate which topic it documents in prose, complementing what `referenceData` documents in structured form under that domain — see "Alternatives discarded" for why the narrower `referenceDataDomains` name was rejected in favor of this. Nodes are always stored **flat**; a tree is never persisted nested. `InformationDomains.resolve(domainId)` reconstructs a domain's nodes into a nested object on demand:

```typescript
resolve(domainId): Promise<Record<string, { label: string, description?: string, data?: Record<string, unknown>, children?: {...} }>>
```

Every node is represented uniformly as `{ label, description?, data?, children? }` regardless of whether it actually has data, children, both, or neither — one predictable shape for any consumer, no special-casing based on what a given node happens to carry (see Alternatives discarded).

## Reasoning

**Flat storage, not nested JSON** — matches `flat-id-based-schema.md`: relationships are expressed by ID reference (`parentId`), never by nesting the referenced record inline. This is the same shape `lbs[]` already uses (nodes + a relation field, tree reconstructed on demand, never stored nested) — not a new pattern, an extension of one already established.

**`parentId`, not `childIds`** — `lbs[]` uses the opposite direction (`lbsNodeIds` on the parent). That direction was rejected here for two reasons specific to how `referenceData` is actually authored: (1) adding a new leaf under an existing parent needs zero mutation of any other record — with `childIds`, it would require also updating the parent's array, a second write for one logical operation; (2) validating that a new node's `key` is unique among its siblings becomes a single filter over `parentId` + `informationDomainId`, rather than a search through every other node's `childIds` for a match.

**`key` unique per-sibling, not globally** — `id` already provides global uniqueness (it's an opaque UUID, generated, never chosen); forcing `key` to also be globally unique would force authors into collision-avoidance naming hacks (`status-open`, `status-in-progress`) for no real benefit, since the only thing that ever needs `key` to be unique is the reconstructed object one level of `resolve()` produces at a time — and JS object keys only need to be unique among themselves at that same level, not across the whole tree. This is the same reasoning `memory-slug-ids.md` already applies (readable identifiers are trusted to authors, not artificially forced into never colliding).

**`resolve()`'s output shape is always `{ label, description?, data?, children? }`, uniformly** — an earlier version made the `data`/`children` part of this conditional: a leaf node (no children) resolved directly to its `data` object, no wrapper. Rejected once stated explicitly, in favor of always uniform: a consumer that has to handle two possible shapes for the same conceptual thing (sometimes wrapped, sometimes not, depending on whether *this particular* node happens to have children) is exactly the kind of ambiguity that caused a real bug earlier in this feature's design (a `null`-vs-object heuristic silently dropping rows — see the discarded frontmatter approach). Uniform-always costs a few characters of extra depth for the common flat case (`status.open.data.color` instead of `status.open.color`); the alternative costs a consumer having to branch on shape. Predictability won.

**`key` is the technical identifier, `label` is the required human-readable one — two separate fields, not one doing both jobs** — `key` is constrained (sibling-scoped uniqueness, used to build the resolved object's property names) and is often not fit for display (`in_progress`, `WIP`). `label` carries no uniqueness constraint and is what any human-facing consumer (e.g. a standard rendering a `referenceData` tree) should show. Matches the precedent already set by `FlowPayloadFieldSchema` (`key` + optional `label`), except `label` is **required** here — unlike a payload field (where the field's own `key` is often self-explanatory enough that a display label is optional polish), a `referenceData` node exists specifically to be read by something that wants to show it, so an unlabeled node is closer to a modeling mistake than a fine default. `name` (the convention used by `Team`, `Role`, `Discipline`) was considered and rejected in favor of `label`, specifically because those entities have no separate `key`-like structural field competing for the "identifier" role the way `ReferenceNode` does — `label` avoids implying it's yet another kind of identifier.

**`resolve()` lives on `InformationDomains`, not `ReferenceData`** — even though the reconstruction walks `referenceData`, "resolve this domain" reads as an operation on the domain being asked for, the same way `Standards.getResolvedContent(id)` lives on `Standards` even though the underlying resolution logic it calls (`resolveBepRefs`) is generic and the raw content lives in separate ZIP storage. `ReferenceData` stays pure CRUD.

**Reconstruction algorithm lives in `utils/referenceData.ts` as a standalone function, `InformationDomains.resolve()` is a thin wrapper** — the original decision (see Alternatives discarded) was to write it directly on the domain entity's `resolve()` method, matching `Members.listResolved()`'s single-consumer precedent. That reasoning held only as long as authoring was the sole consumer. `runtime-readonly-bep-snapshot.md` establishes that a runtime handler's `this.bep` is a plain `structuredClone()`d `Readonly<BEP>`, never an `Entity` instance — so a genuinely second, structurally different consumer exists that can never call a class method. `resolveInformationDomain(domainId, bep)` is exported as a plain function taking a raw `BEP` for exactly this reason: it's the only form callable from inside a runtime handler. `InformationDomains.resolve(domainId)` still exists, now as a one-line wrapper (`resolveInformationDomain(domainId, this.getBep())`), kept for authoring-time ergonomics where an `Entity` instance is available. Both forms are async — see "Live references are JSONata" below.

**Tested against a real `Bep`, not hand-built fixtures** — `test/entities/referenceData.test.ts` constructs everything through `Bep.create()` + `bep.referenceData.add()`, never a bare object literal asserted to match the schema. Forces the tests to exercise real schema-conformant data end to end (validation, referential integrity, and resolution together) instead of a resolution function tested in isolation against data that might silently drift from what the schema actually allows.

**Live references in `data` are JSONata, not a hand-rolled grammar** — a value in `data` (or embedded in a standard's prose) can be `{{<JSONata expression>}}`, evaluated with the raw `BEP` object as its root context — `{{teams[id='COO'].name}}`, `{{project.name}}`, `{{teams.name}}` for every team's name at once. This started as a small hand-written `bep:{collection}:{id}:{field}` grammar, extended repeatedly (support for singular root objects like `project`, ids containing dots like emails, a "get all X" projection) until each extension was re-deriving a piece of an existing, standardized query language. JSONata already solves exactly this problem — filtering a collection by a field, projecting a field across every match, direct property access on non-array values, all with the same syntax — with a maintained reference implementation, so core now depends on it instead of continuing to hand-roll a subset of it. See `docs/adrs/no-async-write-time-validation.md` for the consequence this has on when a reference is validated.

**Deletion-block detection stays a syntactic, not semantic, check** — `referencesEntity()` (used to block deleting an entity a `{{...}}` reference still points to) parses a reference with JSONata's own `.ast()` and looks for a `name` node matching the collection and a `string` node matching the id, anywhere in the tree. It does not evaluate the expression, and does not verify the two are actually part of the same comparison — deliberately conservative: this can false-positive (block a deletion that, semantically, the expression doesn't actually depend on) but never false-negatives on the common case of a direct equality filter. A false positive only costs an unnecessary block, never a missed one — the safe direction to err in, and the same shape of tradeoff already accepted for how broken references are only surfaced as a marker, not prevented outright.

**`generateRuntimeTypes()` generates a named interface per domain, typed per-node from actual observed `data`** — `bep.generateRuntimeTypes()` already generates `BepEffects`/`BepAutomations`/`BepResolvers`/`BepTriggers`/`BepEnv` from real schema-typed fields; `referenceData` extends the same method with `BepReferenceData<PascalCaseDomainId>` per domain plus a combined `BepReferenceData` interface (keyed by domain id) folded into `BepTypes`. Each node's `data` fields are typed directly from `typeof` its own currently-observed value — not inferred or normalized across sibling nodes — because unlike a payload/output schema (declared, not observed), `data` is genuinely free-form JSON with no separate type declaration to draw from; per-node exact typing is the only representation that doesn't invent structure that isn't there. The generated shape mirrors `resolve()`'s own uniform `{ data?, children? }` recursively at every depth, so the generated `.d.ts` and the runtime value it describes never diverge in shape. `generateRuntimeTypes()` itself is async now, for the same reason `resolve()` is.

## Alternatives discarded

**Per-standard frontmatter (`document.data.*`)** — the approach explored and built first, then discarded before commit. Scopes data to one document; nothing sharable across standards, and reintroduces the exact duplication problem live references exist to solve for entities.

**`childIds` on the parent (matching `lbs[]` exactly)** — rejected in favor of `parentId`; see Reasoning above. `lbs[]` doesn't need per-sibling uniqueness validation or fully independent incremental authoring the way `referenceData` does, so its choice doesn't transfer.

**Globally-unique `key`** — rejected; forces awkward manual namespacing (`status-open`) for no benefit once `id` already guarantees uniqueness on its own.

**Context-dependent `resolve()` output (unwrapped for leaves, `{data, children}` for nodes with children)** — rejected in favor of always-uniform; see Reasoning above.

**Group-uniformity type inference for `generateRuntimeTypes()`** — considered generating one merged type per domain with every field made optional across all sibling nodes (e.g. treating "not every `topics` node has a `color`" as reason to mark `color?`). Rejected: this normalizes away real information (which node actually has which field) in exchange for a shorter type, and isn't needed — `data` fields aren't guessed, they're read directly from data that already exists, so per-node exact typing is both simpler to generate and strictly more accurate.

**No type generation for `referenceData` at all, reasoning that `this.bep` already gives a runtime handler full untyped access** — considered, since a handler *can* read `bep.referenceData`/`resolve()` results without any generated types. Rejected: the same argument would apply to effects/automations/resolvers too (a handler could always read `this.bep` directly for those as well), and `generateRuntimeTypes()` exists precisely to replace "correct at runtime, unchecked at compile time" with real autocomplete and compiler-verified shapes — omitting `referenceData` from that would make it the one part of the BEP a runtime author has to remember isn't type-checked.

**Reconstruction logic written directly on the domain entity's `resolve()`, no separate `utils/` file** — the original choice, made when authoring was the only known consumer (mirroring `Members.listResolved()`). Reversed once runtime handlers were confirmed as a second, structurally distinct consumer that cannot call an `Entity` method — see Reasoning above.

**A static `resolve` method on `Bep` itself** — considered when re-deciding where the extracted function should live; rejected as a redundant self-reference (the function already receives a full `bep` object as a parameter — wrapping it in another static method adds no capability, only a second way to spell the same call) and a semantic mismatch with what `Bep` represents (an in-memory instance, not a namespace of utilities). A plain exported function, matching the `resolveLBSCodes` precedent, was chosen instead.

**A single static `Utils` class grouping all utility functions as static methods** — considered as a general repo-wide pattern change, not specific to `referenceData`; rejected because every existing utility in core (`resolveLBSCodes`, `buildParentMap`, `resolveBepRefs`, etc.) is already a plain named export, and introducing a second, competing convention for only the newest utilities would fragment how consumers import from core rather than unify it.

**`referenceDataDomains` as the entity name (this ADR's original name)** — renamed to `informationDomains` once a second use case emerged: associating a *standard* with the same domain it documents in prose, not just grouping structured `referenceData`. `dataDomains` was considered as a middle ground and rejected too — "data" still implied structured records specifically, when the concept is meant to name a topic/subject the project has information about, regardless of whether that information is structured (`referenceData`), narrative (a standard), or both.

**A hand-rolled reference grammar, extended incrementally (`bep:{collection}:{id}:{field}`, then dotted paths, then a `.get("id")` call form to disambiguate ids containing dots, then considering a bolt-on projection syntax for "every X")** — this is the actual path this feature's grammar took before landing on JSONata. Each step solved one real, specific gap (singular objects like `project`, ids with embedded dots like emails, wanting "all team names" not just one) but was re-deriving pieces of an already-standardized query language one at a time. Once the pattern was clear, adopting JSONata outright — rather than continuing to extend a bespoke grammar toward the same destination — was the more honest choice: see Reasoning above.

## Consequences

- `ReferenceData.add()`/`.update()` reject a node whose `informationDomainId` or `parentId` doesn't exist (`checkOutgoingRefs`, automatic for any `ReferenceRule` in `utils/integrity.ts`), a node that references itself as its own `parentId` (schema `.refine()`), and a node whose `key` collides with a sibling's (custom `validate` hook).
- Removing a domain that still has nodes, or a node that is still someone's parent, is blocked the same way any other referential-integrity violation is (`checkRefs`, automatic).
- `{{...}}` references inside a node's `data` are resolved fresh on every `resolve()` call, never persisted resolved (`no-persisted-derivable-data.md`) — the same reference grammar and resolution function already used elsewhere in core, not a new mechanism.
- A node with a `{{...}}` reference in `data` that doesn't currently resolve is **not** rejected at write time — see `docs/adrs/no-async-write-time-validation.md`. Deleting any entity a node's `data` still references — a team, another `referenceData` node, anything reachable by a live reference — is still blocked, the same way any other referential-integrity violation is, generically across every entity via `GetBep.referenceDataRefs`; this check is unaffected because it's syntactic (parses, never evaluates), not semantic.
- `parentId` is validated two more ways at write time: it must point to a node in the *same* `informationDomainId` (a cross-domain parent silently strands the child outside every domain's `resolve()` output — `resolve(domainId)` filters by `informationDomainId` before walking the tree, so a node with a foreign parent is never reached), and it must not create a cycle (walking parentId upward from the node being written must never reach the node's own id again). Neither failure mode crashes or infinite-loops `resolve()` — a single-parent tree structurally can't produce a cycle reachable from a root — but both left affected nodes permanently and silently missing from every domain's output, with no error anywhere, before these checks existed.
- Nothing here defines how a consumer (e.g. the platform's markdown viewer) references or renders `referenceData` from inside a standard's body — same boundary as before: core resolves data, a consumer decides how to display or reference it, that decision is out of scope for `.bep` the format itself.
- `resolveInformationDomain(domainId, bep)` (in `utils/referenceData.ts`) is the form usable from a runtime handler; `InformationDomains.resolve(domainId)` is the form usable during authoring. Both produce identical output for the same BEP state — one is a wrapper around the other, not two independent implementations. Both are async.
- `bep.generateRuntimeTypes()` now includes a `BepReferenceData<Domain>` interface per domain plus a combined `BepReferenceData` interface in `BepTypes`, generated fresh from whatever `referenceData` currently contains — like every other part of this method's output, it goes stale the moment the BEP changes and must be regenerated, not treated as a cached contract. `generateRuntimeTypes()` is async.
- `label` was added after `referenceData` already had write traffic in earlier iterations of this feature (still unreleased throughout) — `normalizeBep` backfills `n.label ??= n.key` on load, so existing nodes stay loadable without a migration step, same pattern as every other backward-compat field addition in core. The `referenceDataDomains` → `informationDomains` and `domainId` → `informationDomainId` renames, and the switch from the old `bep:` grammar to JSONata, have no equivalent backward-compat shim — made while nothing had shipped publicly yet.
